# 주간 공유 — 설계 (확정본)

작성일: 2026-11-06 · 브랜치: `feat/weekly-share`
참고 시안: `docs/mockups/weekly-share-mockup-v2.html` (화면·동작 참고용. 시안 안의 데이터·코드는 가짜이며 옮기지 않는다.)

> 상태: 모든 질문 확정(8번). 구현 착수 대기 — 로컬/테스트 DB 접속(`roi_app` 인증 실패)이 복구되어야 마이그레이션·RLS 테스트를 검증할 수 있다.

## 1. 배경

PM이 담당 고객사별로 이번주/다음주/비고를 주 단위로 공유하고, 관리자는 전체를 조회하며 파트별 실적과 입찰·수주를 본다.
현재 대시보드에는 주 단위 기록, 파트(1·2·3파트) 개념, 입찰 데이터가 모두 없다. 파트 체계(팀 > 파트 > 사람)를 먼저 만들어야 한다.

## 2. 기존 프로젝트 분석 (코드 기준)

### 2.1 고객사·프로젝트·과업 (`prisma/schema.prisma`)

- `Client`: 고객사. `deletedAt`으로 소프트 삭제(보관).
- `Project`: 고객사 아래 계약 단위. `contractStart/contractEnd`, `performanceContract`.
- `Task`: 프로젝트 아래 과업. `unitPrice`, `contractCount`, `contractAmount`, `sortOrder`. `clientId`는 RLS용 비정규화 컬럼.
- 시안은 과업이 4개 고정이지만 **실제는 고객사·프로젝트마다 과업이 다르다.**

### 2.2 담당 PM

- `ClientManager(clientId, userId)`: **다대다**. 한 고객사에 PM이 여러 명일 수 있다.
- `ProjectManager(projectId, userId)`: 표시용. 접근 권한은 `ClientManager` 기준.

### 2.3 로그인·권한

- Auth.js v5(`src/lib/auth/*`), 승인된 사용자는 항상 `role`을 가진다. `requireUser`, `requireRole`(`session.ts`).
- 역할 5종: `SUPER_ADMIN`, `ADMIN`(팀 관리자), `PART_LEADER`(파트장), `SETTLEMENT`(정산담당), `PM`.
- 접근 제어는 DB RLS: `withRLS(ctx, …)`가 `app.user_id/app.user_role/app.team_id`를 주입, 모든 테이블 `FORCE ROW LEVEL SECURITY`. 고객사 기반 테이블은 `app_can_see_client(clientId)` 헬퍼(선례: `ClientMemo` 마이그레이션).
  - 전체 열람: `SUPER_ADMIN`, `SETTLEMENT` / 팀 관리자: 자기 팀(`teamId`) PM이 배정된 고객사 / 파트장: `partLeaderId`=본인인 PM이 배정된 고객사 / PM: 본인 배정 고객사.
- `partLeaderId`는 `app_can_see_client`, `ClientManager`·`ProjectManager`·`Client` RLS 정책(마이그레이션 `20260907000100_part_leader_scoping`)과 `pm-scope.ts`, `data/projects.ts`, `test/rls.test.ts`에서 쓰인다.
- 메뉴: `src/lib/shell/nav.ts`. 정산담당은 지출·청구입금만.
- 마이그레이션은 SQL을 손으로 작성하고 `prisma migrate deploy`로 적용(`migrate dev` 금지).

### 2.4 실적 입력

- `MonthlyPerformance(taskId, year, month, count Float?, amount Int)`, `@@unique([taskId, year, month])`. 과업별 횟수 모드 또는 금액 직접입력 모드(둘 중 하나).
- 저장: `performance/actions.ts#savePerformance` → `data/performance.ts#upsertPerformanceBatch`(내부 `withRLS`, 전체 롤백).
- 화면 `performance/page.tsx`: `고객사 콤보박스 + 연도 + 월 + [조회]`, 아래에 `PerformanceGrid`와 "프로젝트 누적" 표(`listPerformanceTotals(basis:"project")`).

### 2.5 파트·팀 현황 (사용자 관리·팀 관리)

- `Team`(이름만), `User.teamId`. 팀 관리 화면(`admin/teams`)은 최고관리자 전용으로 팀 생성·이름변경·삭제만 있다. 파트 개념 없음.
- 사용자 관리(`admin/users`, 최고관리자 전용): 행마다 `역할 / 팀 / 소속 파트장` 드롭다운. "소속 파트장"이 PM의 파트 역할을 대신하고 있다. 파트 이름·번호는 저장되지 않는다.

### 2.6 재사용 후보

`src/lib/month-range.ts`, `components/charts/*`, `lib/metrics/formulas.ts`·`proration.ts`, `expenses/tabs.ts`+`ExpenseTabs.tsx`(역할별 탭 패턴), `ClientCombobox`, `SelectDropdown`, `lib/action-state.ts`, `lib/validation/schemas.ts`.

## 3. 목표 / 비목표

**목표**
1. **팀·파트 체계**: 팀 관리에서 팀 아래 파트를 만들고, 사용자 관리에서 사람을 파트에 배정한다. 사업운영팀 아래 1·2·3파트를 만들고 파트장(박영걸 1파트 / 문지혜 2파트 / 이지연 3파트)과 PM을 배분한다.
2. 실적 입력 필터를 `[고객사][월 ‹ ›]`로 정리(기존 화면 유지).
3. 신규 메뉴 "주간 공유": 주간 공유 / 히스토리 / 파트 현황(관리자) / 입찰·수주(관리자).

**비목표**: 임시저장, 알림·리마인드, **제출 마감(실제로 없음 — 마감 문구·D-day·지난 주차 표시 모두 만들지 않는다)**, 변경 이력(감사 로그), 시안 코드 이식.

## 4. 규칙

- 주 = 일요일~토요일, 키 = 그 주 **일요일 날짜**(`@db.Date`, Asia/Seoul 기준 계산).
- 주간 공유 1건 = (주, 고객사). 기타 업무 1건 = (주, PM). 같은 키는 1건만(유니크 + upsert).
- "특이사항 없음" = 내용 없이 작성 완료.
- "실적 횟수 수정" = 새 테이블 없이 `MonthlyPerformance`를 그대로 읽고 쓴다(실적 입력 화면과 같은 숫자).
- 두 달에 걸친 주는 월별 조회에서 두 달 모두 보이되 데이터는 1건. 전체·기간 조회에서는 한 번만.
- **한 고객사의 담당 PM 전원이 그 고객사의 주간 공유를 수정할 수 있고, 모든 담당 PM의 화면과 히스토리에 보인다.**
- 관리자(최고관리자·팀 관리자)는 조회만, 수정 불가. 파트 현황·입찰·수주는 관리자만 보임.
- (제외) 기타 업무의 "지원 나간 고객사" 선택과 고객사 히스토리의 "지원" 줄은 만들지 않는다(2026-11-06 결정). "타 고객사 지원"은 구분 칩으로만 남는다.
- 임시저장 없음, 버튼은 [제출] 하나. 내용이 바뀐 저장이면 "수정됨"과 시각 표시. 마감 없음(과거 주도 작성·수정 가능).
- 이미 제출한 카드를 전부 비운 채 제출하면 막고 안내(기록은 삭제하지 않음).

## 5. 데이터 설계

### 5.1 팀·파트 (먼저 만든다)

| 변경 | 내용 |
|---|---|
| 새 모델 `Part` | `id`, `teamId`→Team(Cascade), `name`, `sortOrder`, `createdAt`, `updatedAt`. `@@unique([teamId, name])` |
| `User.partId?` | →Part(SetNull). 파트장·PM 모두 자기 파트를 가진다. 팀 관리자·최고관리자·정산담당은 비워도 됨 |
| 파트장 | `role=PART_LEADER`이고 `partId`가 해당 파트인 사용자. **파트당 파트장 1명**(앱에서 중복 지정 차단) |
| RLS | `Part`: 읽기는 승인된 사용자 전원, 쓰기는 최고관리자만(`Team`의 `team_write_admin`과 동일) |

**기존 파트장 기반 권한(RLS)과의 연결 — 제 판단:** `partLeaderId` 컬럼과 그에 의존하는 RLS 정책 13곳을 그대로 두고, **앱이 `partLeaderId`를 `partId`에서 자동으로 맞춘다**(PM의 `partLeaderId` = 소속 파트의 파트장). 이렇게 하면 이미 검증된 권한 로직을 건드리지 않는다. 동기화 시점은 ① 사용자 저장(역할·파트 변경) ② 파트장 지정/해제 시 그 파트 PM 일괄 갱신. (대안: RLS를 `partId` 기준으로 전부 재작성 — 더 깔끔하지만 변경 범위·위험이 크다.)

**화면 변경**
- 팀 관리: 팀 행 아래에 파트 목록(추가·이름변경·삭제, 파트별 인원수·파트장 이름 표시). 파트 삭제 시 소속 인원의 `partId`는 해제(팀은 유지).
- 사용자 관리: "소속 파트장" 드롭다운 → **"파트" 드롭다운**(선택한 팀의 파트만 표시, 팀을 바꾸면 파트 초기화). 사용자 목록 열 `소속 파트장` → `파트`(파트장 이름 병기).

**데이터 세팅(1회성 스크립트, 환경별 데이터라 마이그레이션 SQL이 아닌 멱등 스크립트):** 사업운영팀 아래 1·2·3파트 생성 → 박영걸·문지혜·이지연을 각 파트의 파트장으로 지정 → **현재 각 파트장 밑에 배정된 PM을 그 파트장의 파트로 이동**. 운영 DB에는 확인 후에만 실행하고, 실행 전 "누가 어느 파트로 가는지" 목록을 먼저 보여 드린다.

### 5.2 주간 공유 테이블

| 모델 | 필드 | 제약 |
|---|---|---|
| `WeeklyShare` | `id`, `weekStart @db.Date`, `clientId`→Client(Cascade), `thisWeek`, `nextWeek`, `note`, `noSpecial Boolean`, `createdById?`→User(SetNull), `updatedById?`→User(SetNull), `createdAt`, `updatedAt`, `editedAt?`, `version Int` | `@@unique([weekStart, clientId])`, index `clientId`, `weekStart` |
| `WeeklyOtherWork` | `id`, `weekStart @db.Date`, `authorId`→User(SetNull), `tags String[]`, `thisWeek`, `nextWeek`, `note`, `createdAt`, `updatedAt`, `editedAt?` | `@@unique([weekStart, authorId])` |
| `Bid` | `id`, `orgName`, `title`, `kind`(신규/갱신), `amount Int`, `dueDate @db.Date`, `announceDate @db.Date`, `status`(준비중/심사중/수주/실주/유찰), `note`, `createdAt`, `updatedAt` — **담당 PM 필드 없음(확인 대기, Q-A)** | index `status`, `dueDate` |

- `createdById`: 최초 제출자, `updatedById`: 마지막 저장자(여러 PM이 같은 건을 고치므로 필요). `editedAt`: 최초 제출 때 null, 내용이 실제로 바뀐 저장에서만 갱신. 내용이 같으면 시각·수정자·`version`을 건드리지 않는다.
- `version`: 동시 수정 충돌 감지용(5.4).
- 작성자 계정이 하드 삭제돼도 기록은 보존(SetNull). 화면에는 "(삭제된 사용자)".

### 5.3 권한(RLS)

- `WeeklyShare` SELECT: `app_can_see_client(clientId)` → 담당 PM·소속 파트장·팀 관리자·최고관리자가 기존 범위대로 열람.
- `WeeklyShare` INSERT/UPDATE: **그 고객사의 `ClientManager`로 배정된 사용자만**. 최고관리자·팀 관리자는 쓰기 정책에서 제외 → DB 수준에서 "관리자 수정 불가" 보장. 파트장은 자기가 고객사 담당으로 배정돼 있을 때만 쓸 수 있음(제 판단). DELETE 정책 없음.
- `WeeklyOtherWork` SELECT: 본인 것, 관리자 범위(최고관리자 전체/팀 관리자 팀원/파트장 소속 PM). 쓰기: 본인만.
- `Bid`: 읽기·쓰기 모두 최고관리자·팀 관리자만.
- 서버 액션에서 `requireRole`로 이중 방어.

### 5.4 여러 PM이 같은 건을 고칠 때 — 작성자 표시와 충돌 방지 (제안)

PM이 여럿이면 한 건을 여럿이 고치므로 "누가 썼나"와 "서로 덮어쓰기"를 함께 다뤄야 한다.

1. **작성자 표시**: 최초 제출자와 마지막 수정자를 모두 보여 준다.
   - 한 사람이 작성·수정: `김서연 · 11/3(월) 10:34 · 수정됨 11/5 09:10`
   - 다른 사람이 수정: `작성 김서연 11/3 10:34 · 수정 이승준 11/5 09:10`
   - 히스토리 표·주간 공유 카드 머리·텍스트 복사에 모두 표기. 기타 업무는 PM 본인 것이라 작성자 = 소유자.
2. **덮어쓰기 방지**: 제출 시 불러온 때의 `version`을 같이 보낸다. 그 사이 다른 PM이 저장했으면 **그 카드만 저장하지 않고** "이승준 PM이 11/5 09:10에 수정했어요. 내용을 확인하고 다시 제출해 주세요"를 표시, 내가 입력한 글은 유지한다. 충돌 없는 카드는 정상 저장. (이 장치가 없으면 나중에 제출한 PM이 앞사람 내용을 조용히 덮어쓴다.)
3. **히스토리 배치**: 공동 담당 고객사는 **담당 PM 각자의 아래에 모두 표시**(요청 사항)하고 "공동 담당" 표시. 건수·월 실적 합계는 고객사 기준으로 중복 제거(공동 담당이라고 두 번 세지 않음). PM 필터는 "그 PM이 담당하는 고객사"를 보여 준다.
4. 변경 이력(누가 어떤 문장을 바꿨는지 전부 남기기)은 이번에 만들지 않는다(비목표). 필요해지면 `WeeklyShareRevision`을 추가하는 별도 작업으로.

## 6. 화면 설계 요약

- **라우팅**: `/weekly-share?tab=batch|history|status|bids`. 관리자 전용 탭은 역할이 아니면 숨기고 서버에서도 거부.
- **실적 입력**: 연·월 숫자 입력 + [조회] → `[고객사][월 ‹ ›]`. 월 스테퍼는 연 경계를 넘나든다. 나머지 화면은 그대로.
- **주간 공유 탭**: `[월 ‹ ›][주차 칩]`. 담당 고객사 카드(이번주/다음주/비고, "이번 주 특이사항 없음", "N월 실적 횟수 수정" 접힘 패널, "지난주 계획 가져오기") + 기타 업무 카드 + 하단 고정바 [제출]. 빈 카드는 저장하지 않음. 마감 문구 없음.
  - 실적 횟수 패널은 `PerformanceGrid`와 같은 과업 목록·횟수/금액 모드를 쓴다. `PerformanceGrid`가 자체 `<form>`이라 중첩 불가 → 공용 입력 컴포넌트로 분리하거나 제출 액션이 주간 텍스트와 실적을 한 트랜잭션에 저장(`upsertPerformanceBatch`가 외부 `tx`를 받도록 최소 수정). **구현에서 가장 신경 쓸 지점.**
- **히스토리**: 파트 > PM > 고객사 > 주차 그룹, 월별/전체/기간, 검색, 텍스트 복사, 본인(담당 PM) 기록 인라인 수정, **작성자 이름 표시(5.4)**. 관리자는 보기만.
- **파트 현황(관리자)**: 파트 카드(누적 실적·달성률) + 12개월 추이 차트 + 분기별/최근 3개월 표 + 파트별 PM 담당 고객사 수·계약 금액. 달성률은 전체 현황 화면의 현재 계산식과 동일하게(구현 전에 `dashboard` 계산식 확인).
- **입찰·수주(관리자)**: 목록 + 등록/수정 모달, 상태, 수주율 = 수주 ÷ (수주+실주, 유찰 제외), 필터(상태·검색). **마감 D-day는 "제출 마감"이 아니라 입찰 일정 정보이므로 유지할지 Q-A와 함께 확인.**

## 8. 추가 결정 (확정)

- **Q-A 확정:** 입찰에서 담당 PM 제외. 입찰 탭은 전체 목록 + 상태 필터 + 검색만. 파트 현황에서도 입찰 표시 없음. 마감일 D-day는 입찰 일정으로 유지.
- **Q-B 확정:** 현재 서로 다른 파트에 걸친 공동 담당 고객사는 없음. 규칙은 단순하게 "고객사의 파트 = 담당 PM의 파트"로 하고, 서로 다른 파트가 섞인 경우의 특별 처리는 만들지 않는다(생기면 파트 카드에 중복 포함되고 "전체"는 고객사 기준 중복 제거).
- **Q-C 확정:** 심명섭·모든 PM은 사업운영팀 소속 → 팀 관리자 권한(팀 기준)으로 전체 열람 가능. 파트 현황·입찰·수주 탭은 최고관리자 + 팀 관리자만. **파트장은 이번 범위에서 제외(나중에 반영).**
- **Q-D 확정:** 5.4(작성자·수정자 표시 + 카드 단위 충돌 방지) 그대로 진행. PM 재배분 = 현재 각 파트장 밑 PM을 그 파트장의 새 파트로 이동.

## 8-1. (이전) 남은 질문 원문 — 모두 위에서 확정됨

- **Q-A. 입찰에서 담당 PM을 빼면** 시안의 아래 기능도 함께 사라집니다. 맞나요? ① 입찰·수주 탭의 파트·PM 필터 ② 파트 현황 카드의 "입찰 N건 진행"과 PM 표의 "진행 중 입찰" 열. (입찰 탭은 전체 입찰 목록 + 상태 필터 + 검색만 남음.) 마감일 D-day는 제출 마감이 아니라 입찰 일정이라 유지하는 것으로 하겠습니다.
- **Q-B. 공동 담당 고객사가 서로 다른 파트의 PM에게 걸려 있을 수 있나요?** 파트 현황에서 그 고객사의 실적·계약금을 어느 파트에 넣을지 정해야 합니다. 제안: 파트 카드는 그 파트 PM이 담당하는 고객사를 모두 포함(공동 담당 표시), "전체" 카드는 고객사 기준 중복 제거 — 이 경우 파트 합이 전체보다 클 수 있음. 대안: 대표 파트 1곳에만 귀속.
- **Q-C. 심명섭 계정이 사업운영팀 소속이고 모든 PM도 사업운영팀 소속인가요?** 팀 관리자 권한은 "자기 팀 PM의 고객사"를 기준으로 하므로 그래야 전체가 보입니다. 파트 현황·입찰·수주 탭은 최고관리자 + 팀 관리자(심명섭)에게만 열고 파트장은 제외하는 것으로 이해했는데 맞나요?
- **Q-D. 5.4의 작성자 표시 + 충돌 방지(제안)** 를 그대로 진행해도 될까요? 그리고 PM 재배분은 "지금 각 파트장 밑에 있는 PM을 그 파트장의 새 파트로 옮기는 것"으로 이해했는데, 다르게 나누실 계획이면 알려 주세요.
